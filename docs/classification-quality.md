# 分类质量诊断与试听试点

程序回归验证的是读取、筛选、保存与执行保护。歌曲的风格、语言和场景适配仍需要核对具体录音与判断依据。分类覆盖所有歌曲，不等于判断全部准确。

## 复核原因

质量规则保留原来的“风格待辨识”“语言待辨识”，并补充四类提示：

| 提示 | 触发条件 | 应检查的内容 |
| --- | --- | --- |
| 录音或语言证据存在冲突 | 既有 `review_note` 为 `true` | 录音版本、平台标记、原歌词或译文错挂等矛盾。 |
| 风格判断把握较低 | 有效 `style_judgment_score` 小于 0.7 | 风格依据是否足够，正式标签是否需要保留待辨识。 |
| 风格或场景依据过于宽泛 | 已知通用模板，包括只附语言说明但没有补风格或场景依据的版本 | 补充可核查的单曲录音依据，以及各场景的收录理由。 |
| 分类依据明确标注待核对 | 原说明明确以“待核”或“待核对”结尾 | 核对说明中尚未确认的曲目、编配、人声或语言，高自评分不能取消这项提示。 |

这些提示表示需要检查，不直接断言歌曲分错。模型自评分未经校准，不能转换成准确率；高分同样不能替代证据。标题里的 Live、Remix、EXPO Ver.、Speed/Sped Up、Slowed、Edit、TV Size、Demo、翻唱或伴奏等字样只作为版本核对线索，不直接确定版本、语种或风格，也不会单独增加“需复核”数量。可用“版本线索”筛选查找这类曲目。

歌词与文字特征可辅助判断语言和主题。节奏、音色、动态、人声强度以及歌单连贯性需要实际录音依据或试听，不能只凭歌词、标题、艺人国籍或宽泛风格名称决定。

## 在工作台修正

“分类成果”的复核筛选可查看所有需复核曲目、证据冲突、低把握、泛化依据、50 首试点或已有草稿。原标签始终保留；展开逐曲修正后选择风格、场景和语言，填写具体理由及录音版本，保存到本地草稿。页面分别展示原结果、修正后标签和各歌单预计增删数量，单曲撤销会恢复原标签。

“分类依据”默认显示原分类；切换“修正后分类”后，歌曲标签、标签选项和待辨识筛选按有效草稿合并计算。因此改成新的语言或场景后，可按新标签查到歌曲。原分类统计、分类歌单和历史核验仍属于原报告，不能证明草稿已经执行；来源过期或草稿不可用时明确回退原标签。

在“歌单增删预览”中选择“逐曲核对”，按歌单查看具体加入或移出的歌曲、修正理由及版本依据。每次读取最多 50 首，可筛选变动方向和翻页。详情绑定父页面的来源和修订；来源或修订变动后清除旧详情，重新读取，避免把两轮草稿的数量与歌曲混在一起。

草稿仅写入 `.organizer/classification-draft.json`，不替换正式报告或执行计划，也不发送账号修改。保存绑定来源哈希、歌曲键及草稿修订号；多个工作台进程同时保存时，OS 文件锁与修订校验会拒绝冲突。页面载入新来源、歌曲或修订后会清除旧的未保存编辑，需要重新核对。损坏或来源过期的草稿保留原文件并停止保存，不会静默重建。

`.organizer/classification-draft.lock` 是常驻锁文件，保存结束后保留文件、释放锁。不要通过删除它绕过并发保护。备份或迁移时保留草稿，公开源码时继续排除整个 `.organizer/` 目录。

## 生成独立诊断草稿

在项目根目录运行：

```powershell
python -X utf8 .\scripts\audit_classification_quality.py
```

默认读取 `artifacts/全库分类-逐曲结果.json`，在 `artifacts/classification-quality-20261007/` 新建两个文件：

- `quality-report.json`：来源哈希、汇总、逐曲复核原因。
- `pilot-review.json`：默认 50 首诊断试点、录音版本核对提示、六种场景收录条件，以及空白评估字段。

来源报告上限为 16 MiB。脚本检查来源格式、序号唯一性和有效评分；输出使用排他新建，任何一个目标文件已存在都会拒绝重跑。来源文件所在目录不能直接作为输出目录。第二轮使用新目录：

```powershell
python -X utf8 .\scripts\audit_classification_quality.py --output-dir .\artifacts\classification-quality-run-02
```

也可显式传入 `--input` 和 `--limit`。来源与报告中的哈希用于确认本轮诊断依据，后续人工复核应保留该来源标识。输出为本地个人曲库草稿，应继续放在被 Git 忽略的目录内。

脚本只读已有来源，没有网络调用或账号执行依赖。质量草稿不能传给分类执行器，也不会替换既有逐曲结果、已批准计划或线上歌单。评估字段为空表示尚未完成核验。

## 50 首诊断试点如何选择

抽样稳定可复现，返回的歌曲继续按来源顺序排列：

1. 优先覆盖数量较少的风格、场景和语言标签，以及冲突、低把握但已正式分类、待辨识、泛化依据和普通高分等诊断层。
2. 为标题包含不同录音版本提示的歌曲保留核对机会。
3. 补足时平衡诊断层，在来源的前、中、后不同区间选择歌曲，并尽量减少同一艺人的重复。

诊断层允许交叠；为了补足样本，同一歌曲按“冲突、低把握正式分类、待辨识、泛化依据、普通高分、其他”的顺序归入首个适用层。各层样本数量与全库占比不一定相同。

这份试点用于发现不同判断方式的问题，属于目的性抽样。它不是随机样本，也不保证有限数量能覆盖所有类别，不能根据试点结果估计全库错误率。样本不足时返回全部歌曲；不重复歌曲，不改动原记录。

## 如何完成评估

先核对歌曲、艺人、专辑和录音版本；标题提示只能帮助定位。试听时至少覆盖有代表性的主体段落、高潮及明显转折，必要时听完整首曲目，并在 `listened_segments` 与 `evidence_sources` 中记录范围和来源。

分别判断风格、语言与场景。场景条件见试点文件里的 `scene_rules`：每个场景都有试听收录条件和排除条件，需按个人偏好校准。例如安静前奏不能证明全曲适合睡前，抒情标签也不能单独证明适合学习专注。

每项 `scene_decisions` 应记录场景、是否适合或尚不能判断，以及具体录音理由。缺少证据时保留未确定；`verified_styles` 和 `verified_language` 未确认前保持 `null`。完成后再填写 `evaluated`，不得用自动生成的说明冒充已试听结论。

审核通过的修正应形成新的本地分类草稿，并保留来源版本、理由和变更差异。只有明确审核过的草稿才能进入后续歌单调整预览；发现某类系统性问题后，再扩展到相应曲目，避免直接重写整个曲库。

## 验证修正后的浏览流程

已安装本地 Playwright CLI 时，可使用[开发文档](development.md)中的真实浏览器验收命令，并给 `verify_classification_quality_browser.py` 传入 `--output-dir` 指定本轮新目录。脚本使用四首临时模拟曲目，核对版本筛选、按修正后标签查找、逐曲加入/移出详情、保存重载与撤销，以及宽窄屏布局。它不调用真实账号，不完成歌曲听辨。
