# 分类质量诊断与试听试点

程序回归验证的是读取、筛选、保存与执行保护。歌曲的风格、语言和场景适配仍需要核对具体录音与判断依据。分类覆盖所有歌曲，不等于判断全部准确。

## 复核原因

质量规则保留原来的“风格待辨识”“语言待辨识”，并补充四类提示：

| 提示 | 触发条件 | 应检查的内容 |
| --- | --- | --- |
| 录音或语言证据存在冲突 | 既有 `review_note` 为 `true` | 录音版本、平台标记、原歌词或译文错挂等矛盾。 |
| 风格判断把握较低 | 有效 `style_judgment_score` 小于 0.7 | 风格依据是否足够，正式标签是否需要保留待辨识。 |
| 风格或场景依据过于宽泛 | 已知通用模板，包括只附语言说明但没有补风格或场景依据的版本 | 补充可核查的单曲录音依据，以及各场景的收录理由。 |
| 分类依据明确标注待核对 | 原说明明确以“待核”或“待核对”结尾 | 核对说明中尚未确认的曲目、编配、人声或语言，高自评分不能取消这项提示。 |

这些提示表示需要检查，不直接断言歌曲分错。模型自评分未经校准，不能转换成准确率；高分同样不能替代证据。标题里的 Live、Remix、EXPO Ver.、Speed/Sped Up、Slowed、Edit、TV Size、Demo、翻唱或伴奏等字样只作为版本核对线索，不直接确定版本、语种或风格，也不会单独增加“需复核”数量。可用“版本线索”筛选查找这类曲目。

重新生成分类报告时，语言核验文件中的 `conflicts` 会作为补充说明保留到语言依据，不采用其中的建议标签。明确的 `review_note` 决定补充说明是否仍需复核；旧格式仅将 `model_text_conflict`、`possible_wrong_lyric`、`possible_description_text`、`recording_version_review` 这四种完整标记视为未解决信号。一般支持说明、未知标记或低把握本身不会自动重开复核；补充说明也不会消除原来仍需复核的状态。已接受的单曲非空语言结论若明确填写 `review_note=false`，则优先于补充信号；空语言仍需辨识。位置重复或补充证据格式无效时停止生成，避免静默丢失依据。这只修复依据的传递，不代表已试听、提高准确率或修改既有报告与线上歌单。

## 生成前核对原始输入

生成分类报告及补齐缺失导出时，必须保留当时用于分类判断的 `artifacts/分类输入-分块01.jsonl`、`02.jsonl`、`03.jsonl`（空分块保留空文件）。逐曲输入记录序号、标题、艺人名字、专辑、时长和元数据可用状态。程序检查序号覆盖完整且唯一，并将标题、稳定去重后的艺人名字和元数据状态与当前来源对齐；元数据不可用时沿用历史艺人回退，有历史专辑或时长时也核对相应字段。旧的无来源声明语言核验列表同样先经过这一检查。

语言核验文件若声明来源 SHA256、覆盖范围或逐曲标题，生成器也会检查这些声明，且同时适用于建议与冲突说明。来源只读取项目内已知分类输入，不能用任意路径代替。生成过程中已读取的文件变化、或原先不存在的可选核验文件出现时，会停止本次生成。错配在导出发布前拒绝，不会自动重排判断、改写复核资料或覆盖原计划。

原始输入缺失时，应找回与原判断对应的资料，或明确重新完成分类判断及复核；不要从当前曲库顺序回填文件，再把它当成当时核对过的证据。新增这一前提是为了阻止按序号把旧复核套给新歌曲。文字字段相同仍不能证明两条记录是同一录音；这些输入不含歌曲 ID，也不能代替音频指纹或试听。对同名、同艺人的版本仍需逐曲核对，不会自动补造历史来源标识。

歌词与文字特征可辅助判断语言和主题。节奏、音色、动态、人声强度以及歌单连贯性需要实际录音依据或试听，不能只凭歌词、标题、艺人国籍或宽泛风格名称决定。

## 在工作台修正

“分类成果”的复核筛选可查看所有需复核曲目、证据冲突、低把握、泛化依据、50 首试点或已有草稿。原标签始终保留；展开逐曲修正后选择风格、场景和语言，填写具体理由及录音版本，保存到本地草稿。页面分别展示原结果、修正后标签和各歌单预计增删数量，单曲撤销会恢复原标签。

“分类依据”默认显示原分类；切换“修正后分类”后，歌曲标签、标签选项和待辨识筛选按有效草稿合并计算。因此改成新的语言或场景后，可按新标签查到歌曲。“清除全部筛选”保留当前分类依据；从原分类歌单打开“待辨识”则明确查看原分类。原分类统计、分类歌单和历史核验仍属于原报告，不能证明草稿已经执行；来源过期或草稿不可用时明确回退原标签。

从分类歌单的“查看分类曲目”进入时，显示该歌单的完整原分类成员，切换到原分类并清除搜索、复核筛选和分页条件；即使草稿已移走该标签的最后一首歌，仍可查看原成员。歌曲上的标签按钮继续按当前分类依据和其他筛选取交集。

用键盘从分类歌单选择“查看分类曲目”或“查看全部待辨识”后，立即定位并聚焦逐曲分类结果标题，可继续阅读加载状态或读取失败提示。鼠标选择时滚动到结果标题，保留鼠标的焦点行为；读取完成后不再重新定位，避免打断随后输入、切换视图或离开页面的操作。

“全部需复核”及其数量按所选分类依据计算：原分类保留原报告的复核提示；修正后分类还会纳入草稿中的风格或语言待辨识，同一首歌只计一次。保存草稿不会自动消除原报告的冲突、低把握或依据不足提示，也不表示核对已完成。该数量针对全部曲库，不随搜索、标签筛选或分页缩小；草稿过期或不可用时按原报告计算。

修正理由和录音依据支持多行输入，可用 Ctrl / ⌘ + Enter 保存；保存失败仍保留输入。“收起修正”仅隐藏编辑，同一来源、修订和歌曲的输入在筛选、分页或离开分类页后返回时保留。“放弃未保存修改”恢复已保存草稿或原标签，不撤销已保存修正。这些输入仅在当前窗口临时保留，关闭窗口或重新载入会清除。

保存失败后，当前编辑仍有效且用户没有移焦或滚动时，焦点返回提交前的输入框或按钮，可继续核对。“刷新分类记录”同时更新本地歌单与任务记录；快照损坏、无法读取或身份冲突时会报错并保留上次可用资料，记录恢复后可主动重试。首次使用或确认已移除快照时仍显示空记录，有有效备用快照时继续按既有规则选择来源。

编辑器显示两个依据字段的字符数量，每项最多 1000 个 Unicode 字符（表情符号按一个字符计算）。超长或包含不支持的控制字符时，会在对应字段说明原因；换行仍可使用。已保存且未改动的修正无需重复保存，按钮和保存快捷键均不会提交，避免无意义地更新修订号并清除其他临时编辑。清空分类搜索后焦点返回搜索框，可直接输入下一次查询。

中文等输入法组合输入期间，歌单名称、分类曲目和歌曲明细搜索保留已确认查询的结果，不用未选定的拼音或候选词更新筛选。确认文字后，曲目搜索仍按 200 毫秒防抖读取；清除搜索会恢复未筛选的结果。

在“歌单增删预览”中选择“逐曲核对”，按歌单查看具体加入或移出的歌曲、修正理由及版本依据。每次读取最多 50 首，可筛选变动方向和翻页。键盘展开、翻页后定位详情标题，收起时回到对应按钮；用户已移焦或滚动时不抢回焦点。详情绑定父页面的来源和修订；来源或修订变动后清除旧详情，重新读取，避免把两轮草稿的数量与歌曲混在一起。

草稿仅写入 `.organizer/classification-draft.json`，不替换正式报告或执行计划，也不发送账号修改。保存绑定来源哈希、歌曲键及草稿修订号；多个工作台进程同时保存时，OS 文件锁与修订校验会拒绝冲突。本窗口收到一首歌保存或撤销成功的确认后，其他歌曲的未保存编辑会继续保留，并采用新修订号提交；保存结果未知时不会自动重复提交。外部来源、修订或草稿可用状态变化仍会清除临时输入并提示重新核对。旧输入不会用于其他歌曲。损坏或来源过期的草稿保留原文件并停止保存，不会静默重建。

连续补录时，可选择“需复核且无草稿”（`review=undrafted_review`），查找当前分类依据下需复核、且尚无当前可用修正的曲目。保存后退出该队列，撤销后返回；其他搜索、标签和分页条件仍取交集。这个队列不代表审核进度：保存草稿不会使复核自动通过，“全部需复核”继续保留来源诊断以及修正后新增的待辨识。草稿过期或不可用时，按原分类和空的适用草稿集合展示，不表示历史上没有保存过修正。队列缩小导致末页失效时返回第 1 页，键盘焦点定位结果标题；用户已移焦或滚动时不抢回焦点。

本窗口确认保存或撤销后，歌曲中“查看分类依据”的展开状态继续保留，主动收起的依据也保持收起。外部来源、修订或草稿可用状态变化时重新收起，便于核对新资料；重新载入或离开当前列表后不承诺保留展开状态。

`.organizer/classification-draft.lock` 是常驻锁文件，保存结束后保留文件、释放锁。不要通过删除它绕过并发保护。备份或迁移时保留草稿，公开源码时继续排除整个 `.organizer/` 目录。

## 分类明细 CSV 导出

`scripts/build_classification_plan.py` 生成的“喜欢的音乐-分类明细.csv”保留单元格内原有的回车、换行、逗号和引号。以制表符、回车或换行开头，或在前导空白后以 `= + - @` 及对应全角字符开头的内容，会加单引号作为文字前缀；已有单引号的内容保持原样。该处理仅作用于 CSV，原始 JSON 和计划中的文字不变。

文字前缀用于降低表格软件将内容解释成公式的风险，不能保证所有软件、导入设置及另存后重开行为一致；本项目未完成 Excel 或 LibreOffice 的执行验证。相关输入边界见 [OWASP CSV 注入说明](https://wstg.owasp.org/latest/4-Web_Application_Security_Testing/07-Injection/21-CSV_Injection/)。

## 生成独立诊断草稿

在项目根目录运行：

```powershell
python -X utf8 .\scripts\audit_classification_quality.py
```

默认读取 `artifacts/全库分类-逐曲结果.json`，在 `artifacts/classification-quality-20261007/` 新建两个文件：

- `quality-report.json`：来源哈希、汇总、逐曲复核原因。
- `pilot-review.json`：默认 50 首诊断试点、录音版本核对提示、六种场景收录条件，以及空白评估字段。

来源报告上限为 16 MiB。脚本检查来源格式、序号唯一性和有效评分。与工作台一致，旧报告缺失或为 `null` 的 `style_judgment_score` 保留为未记录，不补造分数，也不自动当作低分；缺失的 `review_note` 按 `false` 读取。显式填写的无效分数或非布尔复核标记仍会被拒绝。输出使用排他新建，任何一个目标文件已存在都会拒绝重跑。来源文件所在目录不能直接作为输出目录。第二轮使用新目录：

```powershell
python -X utf8 .\scripts\audit_classification_quality.py --output-dir .\artifacts\classification-quality-run-02
```

也可显式传入 `--input` 和 `--limit`。来源与报告中的哈希用于确认本轮诊断依据，后续人工复核应保留该来源标识。输出为本地个人曲库草稿，应继续放在被 Git 忽略的目录内。

脚本只读已有来源，没有网络调用或账号执行依赖。质量草稿不能传给分类执行器，也不会替换既有逐曲结果、已批准计划或线上歌单。评估字段为空表示尚未完成核验。

## 50 首诊断试点如何选择

抽样稳定可复现，返回的歌曲继续按来源顺序排列：

1. 优先覆盖数量较少的风格、场景和语言标签，以及冲突、低把握但已正式分类、待辨识、泛化依据和普通高分等诊断层。
2. 为标题包含不同录音版本提示的歌曲保留核对机会。
3. 补足时平衡诊断层，在来源的前、中、后不同区间选择歌曲，并尽量减少同一艺人的重复。

诊断层允许交叠；为了补足样本，同一歌曲按“冲突、低把握正式分类、待辨识、泛化依据、普通高分、其他”的顺序归入首个适用层。各层样本数量与全库占比不一定相同。

这份试点用于发现不同判断方式的问题，属于目的性抽样。它不是随机样本，也不保证有限数量能覆盖所有类别，不能根据试点结果估计全库错误率。样本不足时返回全部歌曲；不重复歌曲，不改动原记录。

## 如何完成评估

先核对歌曲、艺人、专辑和录音版本；标题提示只能帮助定位。试听时至少覆盖有代表性的主体段落、高潮及明显转折，必要时听完整首曲目，并在 `listened_segments` 与 `evidence_sources` 中记录范围和来源。

分别判断风格、语言与场景。场景条件见试点文件里的 `scene_rules`：每个场景都有试听收录条件和排除条件，需按个人偏好校准。例如安静前奏不能证明全曲适合睡前，抒情标签也不能单独证明适合学习专注。

每项 `scene_decisions` 应记录场景、是否适合或尚不能判断，以及具体录音理由。缺少证据时保留未确定；`verified_styles` 和 `verified_language` 未确认前保持 `null`。完成后再填写 `evaluated`，不得用自动生成的说明冒充已试听结论。

审核通过的修正应形成新的本地分类草稿，并保留来源版本、理由和变更差异。只有明确审核过的草稿才能进入后续歌单调整预览；发现某类系统性问题后，再扩展到相应曲目，避免直接重写整个曲库。

## 验证修正后的浏览流程

已安装本地 Playwright CLI 时，可使用[开发文档](development.md)中的真实浏览器验收命令，并给 `verify_classification_quality_browser.py` 传入 `--output-dir` 指定本轮新目录。脚本使用四首临时模拟曲目，核对版本筛选、按修正后标签查找、逐曲加入/移出详情、保存重载与撤销，以及宽窄屏布局。它不调用真实账号，不完成歌曲听辨。
